## 实现与取舍

| 项目 | 当前实现/决策 | 契约与代价 |
| --- | --- | --- |
| 单帧出站 | 直接传 ProtocolFrame，一个内部完成协调器 | 写 promise 与 flush 都终结才归还预算；取消结果不取消可靠写；多帧一次准入/刷新 |
| AOI 少量变化 | 首条变化存局部引用，第二条才升级容器；单事件独立不可变列表 | 比较后提交、分组/ID 排序、旧 LEAVE 实体、同步序号、异常重试不变 |
| Actor active | 拒绝 stripe/LongAdder 候选，恢复原 AtomicInteger | 分段把成本转移到统计读取，未取得可重复净收益；pending 精确上限不变 |
| Actor 身份 | 保留随机前缀+36 进制序号，采用一次 ASCII 缓冲格式化 | 默认 messageId/trace 共用字符串，显式 trace 不变；不引入 numeric/lazy 身份 |
| EventBus | 框架自有只读成功 stage，嵌套总线按对象身份识别成功 | toCompletableFuture 副本隔离；异步、失败、死信仍为单次状态；不猜测第三方 stage 完成性 |
| Netty 编码槽 | 拒绝，恢复简单同步构造 | 64B 小包分配未降低，CPU 短扫不支持采用；不新增 reader reset API |
| 出站预算预借 | 未达到启用条件，保留精确 AtomicLong | 真实多生产者/多 EventLoop 对照中，共享与独立预算未出现明确扩展性差距 |
| IO 资源治理 | NettyIoResources + 每服务器 channel 生命周期 + 可选 NetworkRuntime 装配 | 不混入业务执行器；默认独占，显式借用不误关其他服务；失败回滚和停止有界 |

active 连续观测短扫（七生产者、一统计线程）：Atomic / stripe / LongAdder 的 dispatch 均值约
9718 / 9548 / 9873 ns；统计读取约 8.1 / 24.9 / 10.3 ns。调度收益处于波动内，统计端代价明确，拒绝候选。
缓冲槽 64B 编码约 255 B/op 未变，CPU 262→278 ns；大包的局部分配下降不足以支撑默认小包路径复杂化。

没有启用原 S4 的跨异步 ByteBuf 借用、MPSC 或直连 RPC，没有改 backlog/flush/GC 默认值。

## 端到端方法和适用边界

`CompileGeneratedLoad.ps1` 每次运行实际 codegen，负载通过生成 DTO/codec/dispatcher/BO，
在计时请求内执行网络→Actor→生成 BO→响应编码。echo 保留为隔离对照。
客户端从计划发送时刻计到完整响应，报告 planned/offered/completed/failed/timeouts/rejected/pending，
超过 3 秒的响应计入超时，不因采样扫表间隔延长而算成功。

GC 对照使用相同 512 MiB 堆上限、`ActiveProcessorCount=8`、固定工作池和预热。该参数是 JVM 的 CPU 数认知，
不是 OS 硬配额或亲和性；服务端固定 1 个接入、4 个 IO、4 个逻辑线程，客户端为独立进程。
客户端在同一 JVM 内预热，预热和测量使用独立计数；请求延迟只统计正式阶段成功响应，超时/失败单列。
测量起止墙钟用于对齐 OS 采样，GC/JFR 文件还包含启动、预热与退出。采样记录有效 flags、GC 日志、
JFR、heap/direct、进程 RSS/private bytes/句柄和 CPU。JFR 分配是采样证据，不据此声称缓存行失效或零分配。
`threads` 来自 ThreadMXBean，指平台线程，不包含 Java 21 虚拟线程；`directBytes` 来自 BufferPoolMXBean，
不代表全部 native 内存。JFR 运行另存 NMT summary，RSS/private bytes 为 OS 进程口径。

30 秒、20,000/s 的 GC 初测每种运行两次，均完成 600,000/600,000；旧入口两端同时选择对应 GC，
服务端暂停最大约 3.05 ms（G1）和 0.020 ms（ZGC），服务端 RSS 峰值约 257–260 MB 与 593–600 MB。
该批元数据未独立保存客户端 flags，只保留为诊断样本，延迟不能单独归因于服务端 GC。

独立 60 秒、10,000/s 的 JFR profile 每种运行一次，客户端固定 G1，仅服务端切换 GC。
两次均完成 600,000/600,000，失败/超时/拒绝/pending 为 0；G1/ZGC 的服务端暂停最大为 3.753/0.018 ms，
RSS 峰值为 296.8/619.7 MB。ZGC 的本机常驻代价更高。JFR ObjectAllocationSample
权重约 11.3/11.8 GB（G1/ZGC），正式测量区间约 9.66/10.04 GB；主要类为 `[B`、`CompletableFuture`、
`DefaultChannelPromise` 与协议缓冲。采样栈数量很少，只用于定位分配类别，不能替代精确分配计数。
flush 阈值是合并次数，不是毫秒等待。建连突发分别测 connect 与首个业务响应，Windows 无队列指标时
不把超时推断为 Linux accept 队列溢出。

Linux EPOLL/OS 队列、跨机、外部中间件和关键发布前 8–24h 趋势均需对应环境单独验证。
本轮本机结果不构成生产容量或通用低延迟 SLO 承诺。

   `RunThirdRoundGcControlled.ps1 -IncludeChain` 固定客户端 G1 并交换生成 DTO 的基线/最终运行顺序。
   `RunThirdRoundWarmBurst.ps1` 原样复制这 23 个 class，增加一个计时前初始化 TLS 的入口；原冷启动样本保留。
5. `AnalyzeThirdRoundJfr.py` 离线汇总采样，`SummarizeThirdRoundLoad.py` 按正式测量起止对齐 OS 资源，
   `CollectThirdRoundEvidence.py` 保存原始数值、命令、源码/制品摘要并验证字节码和请求数量守恒。
   它不读取历史 scaffold 测试结果，不把失败/未完成运行记作通过。

已完成的负载矩阵中，正常 echo/生成 DTO 60 秒（1000 连接、2000/s）及 20,000/s 30 秒均达到
计划请求数且 failed/timeouts/rejected/pending 为 0；TLS 30 秒也完成 60,000/60,000。慢消费者 15 秒
（16 KiB、25 ms 读延迟）约 15.4–16.4k/60k 完成，其余按超时计数，pending 最终为 0。backlog 突发的
非 TLS 1000 连接成功数约 893–952，TLS 突发全部完成连接和首响应但 p99 约 1.02–1.14 秒；
该计时包含 Windows 回环调度、建连、客户端 TLS 冷初始化及握手，不能单独推出服务端握手排队或 Linux accept 队列结论。各 flush 阈值在正常/TLS
样本中均完成，低流量 p99 约 14–22 ms，受本机调度影响；不据此修改默认 flush。

同机服务端和客户端共享物理 CPU/网络栈。`ActiveProcessorCount=8` 不代表隔离了两个 JVM 的 CPU，
低流量的 Windows 定时精度也进入“计划发送→完整响应”延迟。GC 日志包含启动、预热与退出，
JFR 分配权重是采样估计；缺少硬件计数器时不对缓存行失效或伪共享下结论。

## 完整链路复测与 GC 对照

真实 DTO 的首次 60 秒对照存在尾延迟差异，因此补充两组交换顺序的重复：先 final→baseline，再 baseline→final。
每次 1000 连接、2000/s，预热 10 秒、正式 60 秒，客户端固定同一最终驱动；均完成 120,000/120,000，所有错误计数为 0。

| DTO 链路 | 基线 p99 / p999 ms | 最终 p99 / p999 ms |
| --- | ---: | ---: |
| 初测 | 0.183 / 136.315 | 0.307 / 222.298 |
| 复测 1 | 0.219 / 138.412 | 0.209 / 26.345 |
| 复测 2 | 0.324 / 209.715 | 0.283 / 186.647 |

基线与最终实现自身均存在显著尾部波动；没有重现初测的同方向 p99/p999 回退，也不能据此宣称固定比例的
端到端提速。采用收益以受控 JMH 的分配与局部 CPU 对照为依据；这些固定速率测量验证完成能力，不是饱和容量。

## 两小时长稳与资源趋势

真实生成 DTO 链路，1000 连接、目标 2000/s、名义 1 KiB，30 秒预热后正式测量 7200.011 秒。
同时每约 5 秒轮换一个空闲连接，并持续执行 Scene/AOI/FrameSync 对象创建与释放。
planned/offered/completed 均为 **14,400,000**；failed/timeouts/rejected/pending/unexpectedResponses 均为 **0**，
实际完成 1999.997/s，重连 **1439** 次。延迟 p50/p95/p99/p999 为 **0.0645/0.1106/0.1659/0.3133 ms**，
最大 151.625 ms；不能用分位数隐去这次最大值。两个进程退出码均为 0，已生成 `completed.json`。

direct 仍为 16,809,984 B。未在停机前强制 GC，不能把 allocator/待回收缓冲仍计入 MXBean 解释为已释放，
也不能仅凭这个单点判定泄漏。进程已退出，其 OS 资源由系统回收；服务器级资源释放另由生命周期测试验证。

服务端 heap 采样范围约 19.1–187.4 MB，中位数约 101.6 MB。各 15 分钟窗口的采样低水位从约 19 MB

GC 后存活量/堆对象对照这一验证边界，不能写成“内存完全平稳”或“证明无泄漏”。

JFR 临时目录的分段文件约每 17 分钟增加一个，与句柄的少量增加相符，观察记录已保存；未做 OS 句柄归属核验，
仅据这个相关性不能排除所有资源泄漏。本轮验证了该负载下两小时持续完成和正常退出，没有测量饱和容量。

长稳 JFR 的选定事件覆盖整个正式区间，共 984,236 个分配样本、374 个执行栈样本及 1580 个 GC 暂停事件。

并非保留内存或精确 B/op。主要分配类别为 byte[]、CompletableFuture、Object[]、HeapZeroBuffer、ProtocolFrame。
执行栈样本很少，不据此计算精确 CPU 占比。原始 JFR、流式导出的压缩 JSON、分析结果和 SHA-256 全部保存；
采样不能代替缓存行/硬件计数器或长期存活对象分析。
