# 审计 B4：网络、RPC、发现、缓存与数据映射迁移

日期：2026-10-08。适用于当前 0.x 开发分支；本批不发布版本，不增加旧格式兼容层。源码与本批测试为结论依据，历史“已修复”不作为验收证据。

## 接入变化

| 入口 | 当前行为与迁移动作 |
| --- | --- |
| `NetworkTuning` | canonical 构造从 8 参数改为 10 参数，追加 `maxOrderedInboundFrames`、`maxOrderedInboundBytes`。既有 7 参数默认装配仍可用；默认顺序入站预算为每连接 1024 帧/16MiB。用 `withOrderedInboundLimits(frames, bytes)` 配置，`withTcpFrameOrderPreserved` 保留这些预算。KCP runtime 重建配置时保留全部顺序字段。 |
| TCP 顺序入站 | 预算包含活动 handler、等待响应完成的帧及排队帧；每帧按 payload + extension + 128 字节计费。超限报 `INBOUND_OVERFLOW` 并关闭，活动帧在物理完成后释放；已有 production lifecycle 更严的限制仍有效。仅在 TCP 顺序模式启用，不是 JVM 内存精确上界。 |
| 连接关闭错误 | `NettyConnection.close` 的失败从 `SEND_FAILED` 改为 `CONNECTION_CLOSE_FAILED`（`ZERO-NET-CONNECTION-CLOSE-FAILED`）；按错误码匹配的监控和业务分支须同步。出站 `OUTBOUND_OVERFLOW` 码保留，消息区分静态超限、不可写及局部/全局暂时耗尽，仅附可信计数。 |
| `CachePolicy` | canonical 构造从 7 参数改为 8 参数，追加正数 `writeTimeout`，默认 3 秒；原 6 参数默认装配仍可用。`loadTimeout` 与 `writeTimeout` 各自独立。自定义策略须显式补齐写入观察期限。 |
| 缓存写入超时 | put、invalidate、条件失效与回填的观察期限从准入开始，含排队时间。超时返回 `WRITE_TIMEOUT`（`ZERO-CACHE-WRITE-TIMEOUT`），结果未知；已接受操作仍可能随后执行/提交。同键屏障、引用和容量只在实际完成后释放。超时/取消不证明未写入，不据此自动重试，应用应按版本及幂等契约核验。 |
| 缓存健康恢复 | L2 成功只能确认该操作开始时的失败代际；冷却结束且补偿/外部 backlog 为零后才恢复。L1 命中、时间流逝和清队列本身不能确认后端恢复。累计失败数不清零。 |
| 外部写回监控 | 保存 `markWriteBackFailure()` 返回的累计故障凭据；对应外部写回实际恢复成功后调用 `confirmWriteBackRecovery(ticket)`。仅最新未确认凭据有效；true 只表示外部故障被确认，不等于整体健康。Redis wrapper 同步提供该入口。外部成功事实由调用方负责；内部补偿故障不需要外部凭据。 |
| Nacos 监听历史 | `listenerFailures()` 只保留最近 256 条、按发生顺序返回不可变快照；`listenerFailureCount()` 为累计数，`droppedListenerFailureCount()` 为丢弃历史数。需要完整历史的使用方应自行导出观测，不能把快照视作完整历史。 |
| 泛型组合键 | KeyCodec/KeyGenerator 的父类和接口绑定沿继承链解析，具体键正确构造。无法解析的原始/类型变量键抛 `MAPPING_INVALID`；只有明确 String/Object 键保留文本组合行为。自定义 SPI 须在具体实现中绑定键类型。 |

## 网络与 RPC 语义

Netty 缓冲桥按 allocator 的容量策略扩容，保持 ZeroWriter 绝对索引与已有字节，受配置上限和 ByteBuf maxCapacity 双重限制。此修改减少连续增长时的扩容次数，没有以单元测试推导生产吞吐提升。

TCP `doStart` 对 Error 与异常均尽力回收本次资源，保留原失败，清理失败附加 suppressed；IO 组关闭尽力处理各组。借用 IO 仍归组合根所有。公共 `AbstractLifecycle.start` 的既有包装语义保留：Error 作为原始 cause 保留在生命周期异常中；本批没有改变核心生命周期错误契约，也不承诺 JVM OOM 时清理必定成功。

Kafka 发送与消费都按 `timeoutAt <= now` 判过期。`HANDLER_STARTED` observer 返回后再检查期限，避免观察器消耗最后预算后仍开始 handler。已开始的业务副作用不会被超时回滚。metadata/verifier/路由/期限拒绝统一记录一次 `REQUEST_REJECTED`；oneway 仍不回响应。pending 使用毫秒精度，小于 1ms 的有效超时预算明确拒绝。

Kafka envelope 增加 32MiB 整包预算，编码增长前检查，解码在解析/复制字段前检查；payload 16MiB、单字符串 1MiB 和现有安全 metadata 字段限制仍生效，线版本保持 1。有效对象还受更严格字段限制；总预算主要阻止畸形整包继续解析。Kafka fetch 是软限制，codec 无法阻止 Kafka 客户端已经分配的原始 byte[] 或 broker 大批次，需共同配置 producer、topic/broker 与消费并发。

Nacos TTL 仍为可配置最终一致缓存。查询加载时捕获失效代际，事件、成员变化与 stop/restart 后的旧查询不能重新填入缓存；SDK IO 和业务回调不进入缓存短锁。全局代际可能使无关服务事件期间的查询放弃填充，增加 SDK 查询次数，不引入全服务订阅。

## KCP 静默与迁移

响应批次逐帧等待本地接收阶段；首个失败停止后续响应，handler/响应批次结束后才推进下一业务，关闭后的迟到阶段只回收一次预算。这里的成功仍是本地算法接收，不等于远端 ACK。

冻结或客户端静默后禁止业务 drain，包含 ACK-only 包。适配层仅跟踪未投递 PUSH 的 sequence/frg/length 元数据，最多 `2 * receiveWindow`（当前最多 512 段），覆盖算法接收队列和乱序缓冲，不复制 payload、不反射依赖内部、不改变线格式或快照。

只有实际完整 mergeRecv 后才推进已投递水位；合并前校验连续序号、frg 倒数、长度与 peekSize。已投递旧 PUSH 重传仍可进入算法回 ACK；静默后新的或尚未投递的 PUSH 以 `INVALID_MESSAGE` 关闭源会话，原因 `receive.quiescent_push`，不确认该业务已经接收。延迟 FEC 恢复也经过同一门控，回调内关闭不会重复释放 FEC 预算。

静默前的不完整/乱序接收使 drained=false，迁移不能提交；无法继续安全交付时由既有迁移超时关闭。该策略可能保守拒绝迁移，应用不得在收到 QUIESCED 前切换目标。没有 unfreeze 或业务接收队列快照契约。

## 保留的存储与缓存契约

- `markDirty` 不重置键级失败隔离；修复数据后显式 `retryFailed`。
- durable APPLIED 收据保留 operationId 幂等性，仍计容量，compact/restart 不删除；满额拒绝，不自动开放操作 ID 重用。
- executor 在 append 前拒绝不产生耐久确认；append 后重放被拒绝仍保留 PENDING。durable 以本地 force 完成作为确认，不代表远端已写成功。
- `DurableRecord.sameEnvelope` 比较所有元数据（含 encodedAt）和 payload 内容，不再完整编码两次；不改 record equals/hashCode、持久化字节或 CRC 规则。
- 补偿队列满时读失败、不回填 L1；本地容量淘汰为插入顺序，不是 LRU。
- PostgreSQL 外部 DataSource 必须提供 autoCommit=true；手动事务连接被拒绝并归还，不强制提交调用方事务。

## 验证证据与边界

本批关键负向回归覆盖 TCP 积压、Kafka observer deadline/拒绝观测、Nacos 失效回填/历史容量、缓存条件失效/恢复、多级泛型组合键、KCP 异步响应批次。各自实际修复前失败日志和修复后结果保存在本机任务归档，未把编译/命令错误当作行为复现。

验证包括 EmbeddedChannel、受控 future/SDK fake、本机真实 TCP/UDP、加密/FEC、内存 session store 双节点迁移，以及本地耐久子 JVM 突然退出恢复。全 reactor quality（含 benchmarks 编译）最终命令与统计见审计 B4 验收记录。benchmarks 编译不等于执行 JMH。

未运行真实 Kafka/Nacos/Redis/PostgreSQL 外部集成、跨机器迁移、生产容量、长稳、OS 强杀/磁盘丢失或 JVM OOM 演练。`tasks/` 被 Git 忽略，仅作本机证据；Git 内保留本迁移说明及审计验收摘要。
